# AI Atlas — Bug Findings (2026-09-03)

Reviewed the most recently touched code (last 5 commits) and verified suspicions directly against the live Supabase project. One confirmed live bug, two latent versions of the same bug, and a couple of secondary issues.

## 1. Stale "latest data update" timestamp — confirmed live bug — ✅ FIXED

**File:** [`lib/data.ts:699`](lib/data.ts#L699) — `fetchTimestampRows`, used by `getLatestAtlasDataUpdateCetDisplay` (shown on 8+ routes: home, `/quality`, `/industries`, `/industries/[industry]`, `/blog`, `/blog/[slug]`, `/use-cases`, `/news`, admin).

Does an **unpaginated** `select("created_at")` with no `.order()` or `.range()`:

```ts
const createdOnly = await supabase.from(table).select("created_at")
```

Supabase's REST API caps unpaginated selects at **1000 rows**. Checked the live tables:

- `AI_Atlas_Use_Cases`: **1571** rows (571 silently dropped)
- `AI_Atlas_Companies`: **1190** rows (190 silently dropped)

Reproduced directly: the unpaginated fetch already returns a stale max timestamp for use cases (`2026-09-02T22:07:03.8Z` vs the true max `2026-09-02T22:07:05.5Z`). The gap is small today but will grow — and since there's no `.order()`, whichever 1000 rows Postgres happens to return first has no guaranteed relationship to recency, so entire new batches of data can be excluded from the "latest update" calculation.

This is the exact same 1000-row cap that commit `c5ad0fd` already found and fixed for companies via `fetchAllCompanies()` — that fix just wasn't applied here.

**Fix applied:** replaced the "fetch all rows, compute max in JS" approach with asking the database directly for the single newest row per table (`.order("created_at", { ascending: false }).limit(1)`) — cheaper than fetching up to 1000+ rows, and has no row cap to hit. Verified against the live database: now returns the true max (`2026-09-02T22:07:05.539Z`) instead of the previously-truncated one.

## 2. Same bug, second location — confirmed live — ✅ FIXED

**File:** [`lib/data.ts:181`](lib/data.ts#L181) — `getCompanies()`.

Another unpaginated select on `AI_Atlas_Use_Cases`:

```ts
supabase.from("AI_Atlas_Use_Cases").select("id, company_id, \"URL\"")
```

With 1571 rows, this drops ~571 of them, degrading `officialWebsiteById` — the fallback that fills in a company's website from its use-case URLs when `website_url` is empty. Lower impact than #1 (cosmetic fallback data only), same root cause.

**Fix applied:** now uses `fetchAllUseCases()` (see #3), which pages through the full table.

## 3. Same bug class, not yet triggered — time bomb — ✅ FIXED

**File:** [`lib/data.ts:589-597`](lib/data.ts#L589-L597) — `getUseCasesCatalogRows` (admin/unpublished path).

Hardcoded exactly two 1000-row pages (`range(1000, 1999)`) to cover "currently ~1072" use cases per the code comment. Actual live count is now **1571**, so it was still under the 2000-row cap today — but it would have silently truncated again once the table passed 2000 rows, same as the bug `c5ad0fd` already fixed once for companies. It also selected `*` (including the heavy `content` column) for the overflow page only, inconsistent with the main page's trimmed column list.

**File:** [`lib/data.ts:508-520`](lib/data.ts#L508-L520) — `getUseCasesWithCoords` (powers the globe).

No pagination guard on its use-cases query either. Was only safe today because it's always called with `publishedOnly: true` and the published count (676) is under 1000. Would have truncated globe data once published use cases cross 1000.

**Fix applied:** generalized `fetchAllCompanies` into a shared `fetchAllRows(supabase, table, opts)` helper (`lib/data.ts:470`) that pages through a table with `.range()` until a page returns fewer than 1000 rows. Added `fetchAllUseCases()` on top of it (mirrors `fetchAllCompanies`) and switched `getCompanies()`, `getUseCasesWithCoords()`, and `getUseCasesCatalogRows()` to use it — removing the old two-page hack and the `select("*")` inconsistency in the same pass. Verified against the live database: paginated fetch returns exactly 1571 use case rows and 1190 company rows, matching the true `count(*)` for each table, with no duplicates.

## 4. Open URL-fetch proxy — security — ✅ FIXED

**File:** [`app/api/news-image/route.ts`](app/api/news-image/route.ts)

Accepted any `url` query param, fetched it server-side, and (with `mode=image`) returned the response bytes to the caller — with no allowlist restricting it to known news-source domains. Anyone could call this endpoint to make the server fetch and relay arbitrary internet content (SSRF-adjacent / open-proxy abuse surface; internal-metadata risk was limited since this runs on Vercel, but it was still unrestricted server-side fetch + bandwidth abuse).

**Fix applied:** added `getNewsSourceHostnames()` (`lib/data-news.ts`) — derives the set of hostnames from published `AI_Atlas_News.url` values (the only legitimate source of `url` params, per `components/news/news-card-image.tsx`), reusing the already-cached `getCachedNewsItems()` (5 min). The route now checks the requested hostname against this allowlist before doing any fetch, returning `403` for anything not on it.

Verified live: the allowlist currently contains 70 real article hostnames (arstechnica.com, simonwillison.net, youtube.com, etc.) derived from 457 published news rows. Smoke-tested against a running dev server — an attacker-style URL (a cloud metadata address, `169.254.169.254`) and an arbitrary domain (`example.com`) are both rejected with `403`, while real published-article URLs (including the YouTube-thumbnail special case) still resolve correctly.
